# Summary — Fix ExDoc warnings and close the CI gap

## Outcome

`mix ci` is green end to end (exit 0). It had been red on `docs --warnings-as-errors`.

## What was wrong

18 warnings from 9 distinct causes — ExDoc runs the html and epub formatters and each reports
independently.

The more consequential finding: GitHub CI ran plain `mix docs` (`ci.yml:260`), which exits 0
regardless of warnings. `--warnings-as-errors` was applied to *compile* in CI but never to *docs*.
So the local `mix ci` alias was strictly stronger than the required `ci-gate` lane, and these 9
warnings had never been able to fail a PR. No baseline or tolerance mechanism existed anywhere in
the repo — it was simply an unguarded surface.

## Changes

| Cause | Fix | Files |
|---|---|---|
| Relative links to non-extras | Absolute GitHub URLs | `guides/getting-started.md`, `guides/user-flows-and-jtbd.md` |
| `File.create/3` → stdlib `File` | Fully qualified | `guides/recipes.md` (×2) |

| Unguarded docs lane | `mix docs --warnings-as-errors` | `.github/workflows/ci.yml` |
| Undocumented convention | New "Documentation Warnings" section | `CONTRIBUTING.md` |

## Decisions

**De-linked rather than promoted.** `LatticeStripe.ObjectTypes` and `BillingPortal.Guards` stay
`@moduledoc false`. Promoting either to silence a doc warning is a one-way semver door and would
force regenerating `priv/api/current.txt` plus adding a `groups_for_modules` entry. The de-link
matches existing style: `check_drift.ex:11` already wrote "ObjectTypes registry" unbackticked in
the same moduledoc that warned three lines above.

**`webhook.ex:376` was rephrased, not just unbackticked.** It is a *public* function's doc that
pointed adopters at a module they cannot open; describing the behaviour is the better doc
regardless of the warning.

**`release.yml` and `publish-hex.yml` left on plain `mix docs`.** Both run after `ci-gate` has
already proved the docs build clean. Failing a *publish* on a doc warning would trade real outage
risk for no new signal.
