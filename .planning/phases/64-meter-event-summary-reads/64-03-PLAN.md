fact in it was surprising enough to be written down as a verified finding during discussion.

    Open with a one-line definition, then a paragraph naming the wire object `billing.meter_event_summary`,
    the `mtrusg_` id prefix, and the single endpoint `GET /v1/billing/meters/:id/event_summaries`. State
    that this is the only path — there is no top-level collection and no retrieve-by-id — which is why the
    parent meter id is a positional argument rather than a param.

    Add a warning admonition block, in the `> #### ... {: .warning}` form used at `active_entitlement.ex`,
    carrying the two facts most likely to produce a silently wrong number:

    First, the returned object has no customer field. It has exactly seven fields and none of them names the
    customer, and it cannot be expanded to add one. The customer was an input to the query, never an output.
    A reconciler that lists summaries for several customers and merges the results has lost the attribution
    unless it kept the association out of band. Name the warning sign explicitly: grouping a merged list by a
    customer field is not possible because that field does not exist.

    Second, summaries are eventually consistent. Stripe's own spec says so, there is no freshness field on
    the object, and no SLA is published — so a caller cannot tell how stale a figure is. Give the guidance in
    user-experience terms rather than API terms: label the figure with the time it was fetched, never present
    it as live, and never use it as a billing source of truth, because Stripe bills from the meter and not
    from these summaries.

    Add a `## The window boundary is ambiguous` section, or fold it into the listing section, documenting
    F-08 honestly: the `end_time` query parameter and the `end_time` object field are both described as
    exclusive, while `aggregated_value`'s own description on the same object says the aggregation covers
    start through end inclusive. Two of the three say exclusive. State that Stripe's specification contradicts
    itself here, that all three descriptions ship verbatim into every SDK's generated documentation so
    adopters will meet the contradiction elsewhere too, and that this library asserts neither reading.
    Do not resolve it and do not pick a side.

    Add a `## Listing` section covering the truncation trap. The limit ranges from 1 to 100 and defaults to
    10. A 31-day hourly window is 744 buckets; a caller who sums the ten returned rows without checking
    whether more exist gets a plausible number that is roughly one and a third percent of the truth. Present
    that figure as an illustrative example assuming even usage across buckets, not as a law. Then teach the
    total-versus-series split, which is the actual fix: omitting `value_grouping_window` returns one
    server-aggregated bucket in a single request, with no pagination and no client-side float summation,
    which is what an admin screen showing "usage this period" almost always wants. Use a `stream!/4` example
    for the series case and cross-reference `LatticeStripe.List`'s existing memory guidance rather than
    restating it.

    Add a `## Timestamp alignment` section, brief, stating that Stripe requires minute-aligned timestamps on
    every query and hour- or UTC-day-aligned timestamps when `value_grouping_window` is set, that
    `subscription.current_period_start` and its sibling derive from the billing cycle anchor and land on an
    arbitrary second so they are almost never aligned, and that this library raises before the network rather
    than aligning silently. Do NOT state how often this bites callers — the mechanism is verified but the
    incidence is not, and issue archaeology found no public bug reports (D-12). The guard itself lands in

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
