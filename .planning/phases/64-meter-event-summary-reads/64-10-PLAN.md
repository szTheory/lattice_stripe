<planner_assumptions_surfaced>
These edge questions were raised by the deterministic edge probe and could NOT be resolved from any
available source. They are recorded here rather than silently dropped, and none of them is guarded or
claimed anywhere in the shipped code or documentation.

1. **MTR-01 adjacency — is the window's end boundary inclusive or exclusive?** Stripe's own specification
   contradicts itself: the `end_time` query parameter and the `end_time` object field both say exclusive,
   while `aggregated_value`'s description on the same object says the aggregation covers start through end
   inclusive. Two of three say exclusive. **Disposition:** documented as an ambiguity in the moduledoc and in
   the guide, with neither reading asserted. This is deliberate and must not be "resolved" by a later
   contributor without a live probe.

2. **MTR-04 concurrency — what ordering or freshness guarantee applies when usage is reported concurrently
   and read back immediately?** The read surface is documented as eventually consistent with no freshness
   field and no published SLA, so no bound exists. The encoder's own purity is proven; the ingestion
   pipeline's behavior is not knowable offline. **Disposition:** the guide tells readers to label a figure
   with its fetch time and never treat it as a billing source of truth. No timing claim is made.

3. **O-01 — does Stripe's parser accept exponent notation for a payload value?** Unresolved. Requires a live
   test-mode probe with a real customer and a wait on the asynchronous error report. **Disposition:** the
   guide ships the outcome-independent sentence, which stays correct under all three possible answers.
   Blocks the deferred change to the encoder's stringification.

4. **O-02 — maximum and minimum window span, and any lookback limit, for summary reads.** Undocumented
   upstream; the verified 35-day limit applies to ingestion, not reads. **Disposition:** say nothing.

5. **O-03 — the actual error code Stripe returns for a misaligned timestamp.** Absent from the API errors
   reference, from every SDK, and from the spec's error enums. **Disposition:** never pattern-matched, never
   named. This absence is precisely why the alignment guard exists.

6. **O-04 — do deactivated meters still serve summaries?** Believed yes, unverified. **Disposition:** not
   claimed.

7. **O-05 — are zero-value buckets emitted for empty periods, or skipped?** Unresolved.
   **Disposition:** the guide gives the defensive rule regardless — fill chart gaps by start time, never by
   index.

8. **O-06 — is the guide's synchronous-only classification of three error codes correct, given that all
   three also appear in the asynchronous error-report enum?** Unresolved offline. **Disposition:** those
   three rows are labelled unverified in the rewritten table rather than restated.

If any of these is later resolved by a live probe, the correct response is an additive documentation change,
not a retrofit — every sentence shipped was chosen to remain true under every possible answer.
</planner_assumptions_surfaced>
