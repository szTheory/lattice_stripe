    Lead with an input-to-wire coercion table rather than prose rules. A table states the arbitrary-keys,
    decimal-string, float-hazard, nesting-rejection and nil-vanishing facts all at once and is far clearer
    than five paragraphs. Give each row an Elixir input, the resulting wire fragment, and a one-line verdict.
    Every value in the table must be one you have reproduced yourself against the shipped encoder.

    Then state four rules, ordered by what they cost the reader who gets them wrong.

    Rule one, flat only. Payload values must be strings as far as Stripe is concerned; this library's encoder
    will happily flatten a nested map into bracketed keys, so the SDK lets you build a request Stripe
    refuses, and Stripe's rejection message names the offending kind. This is documented nowhere today.

    Rule two, decimals as strings. Passing a decimal as a string survives byte-exact to at least 36
    significant digits. Passing it as a float goes through Elixir's default stringifier, which flips to
    scientific notation at 0.00001 — one decimal place away from values people genuinely bill on, such as a
    per-token cost. Use 0.00001 as the example, not a smaller number; the point is that the cliff is close,
    not that it exists somewhere far away. Note that Elixir's threshold is the narrowest in the ecosystem:
    one comparable runtime flips a decimal place later, and one reference SDK's formatter never emits
    exponent form at all. Also note that binary floating point produces artifacts, so adding two ordinary
    decimals can yield a long tail of digits.

    On whether Stripe's parser accepts exponent notation, ship the outcome-independent sentence and nothing
    more: pass decimals as strings, because Stripe does not document whether its parser accepts exponent
    notation, so do not rely on it either way. That sentence is correct whichever way the open question
    resolves, and it gets stronger rather than being corrected if a future probe shows a rejection. Do not
    speculate about which happens.

    Also state that a nil value vanishes from the encoded body entirely rather than being sent as empty, so a
    zero must be sent as a string zero.

    Rule three, cardinality. Dimension values become distinct series; keep the value set bounded and never
    put an unbounded identifier in a dimension.

    Rule four, and this is the one that saves an adopter a wasted week: on the generally available API you
    cannot read usage back grouped by a custom dimension. Stripe stores dimensions but offers no way to group
    by them — the summary object has no dimensions field, a group-by parameter is rejected, and the canonical
    configuration documentation does not mention dimensions at all. Dimension grouping exists only in
    preview. The workarounds are one meter per dimension value, or your own store. State this plainly; no
    other SDK's documentation says it.

    Close the section by connecting it to the error report: the only correlation key Stripe returns for a
    failed meter event is the HTTP idempotency key of the failing request, and this library auto-generates
    one when the caller does not supply it, so by default that key maps to nothing in the caller's database.
    Pass a domain-derived idempotency key on every meter event write. The existing fire-and-forget recipe
    already does this; make the reason explicit rather than leaving it as an unexplained argument.

    Add a `## See also` or inline cross-reference to the new reading-usage-back section, so a reader who
