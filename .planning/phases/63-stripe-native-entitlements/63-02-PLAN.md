<objective>
Complete the `ActiveEntitlement` read surface — `retrieve/3` for one entitlement, `stream!/3` for all
of them — and prove the pagination path with the eight named assertions that make the reconciler
trustworthy.

Purpose: `stream!/3` is the reconciler-critical piece. Stripe's `limit` defaults to 10, so any
consumer that calls `list/3` once and stops has silently truncated. This exact bug class shipped in
stripe-node, stripe-php, stripe-java, and both Stripe-sync-engine forks — and it is literally the bug
the downstream adopter is carrying today. stripe-mock cannot prove pagination (it returns one item
per list and ignores `limit`/`starting_after`), so the Mox-at-Transport multi-page pattern is the
only place this is genuinely provable.

Output: the finished read surface plus `active_entitlement_stream_test.exs`, whose
`"page 2 preserves the customer filter"` test is the single highest-value assertion in the phase.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller → `LatticeStripe.List.stream!/2` | The caller's tenant scoping (`customer`) and Connect scoping (`stripe-account`) must survive being rebuilt into every subsequent page request. |
