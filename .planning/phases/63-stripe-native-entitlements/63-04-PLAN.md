<objective>
Ship `LatticeStripe.Entitlements.ActiveEntitlementSummary` — the typed decode of the webhook-only
summary object — with its nested entitlement list correctly typed *and* correctly cursored, plus the
blessed reconciler entry point.

Purpose: ENT-05's requirement text says the payload must "deserialize without being dropped", but
nothing in the SDK drops id-less objects today — `Client.build_decoded_response/6` and
`ObjectTypes.maybe_deserialize/1` key only off the wire `"object"` string, and `List.first_item_id/1`
and `last_item_id/1` already return `nil` gracefully. So "make deserialization id-tolerant" would be
a no-op. The real deliverable is the typed module itself: a struct with **no** `:id` field, a nested
`%LatticeStripe.List{}` whose data is typed, and a reconciler helper that never asks the caller to
learn that Stripe inlines only ten.

The hazard is ordering. `List.from_json/3` derives `_last_id` by matching `%{"id" => id}` on raw
string-keyed maps; typed structs do not match that pattern. Type the data first and `_last_id` becomes
`nil`, at which point the next-page builder either silently truncates at ten or re-requests page one
forever — with zero test failures. This exact bug shipped in stripe-node, stripe-php, stripe-java, and
both Stripe-sync-engine forks.

Output: the module plus a pure `from_map/1` unit test — no transport at all, because no HTTP endpoint
serves this object.
</objective>
