## Summary

Phase 41.1 should be planned around a real Stripe sandbox proof, not `stripe-mock`, because Stripe’s Quote accept flow is documented to create downstream billing objects, while Stripe’s own `stripe-mock` project describes itself as basic sanity-check tooling and the repo’s Phase 41 runtime evidence already reproduced `invoice=nil`, `subscription=nil`, and `subscription_schedule=nil` after `Quote.accept/3` under local `stripe-mock`. [CITED: https://docs.stripe.com/api/quotes/accept] [CITED: https://github.com/stripe/stripe-mock] [VERIFIED: `.planning/phases/41-quote-lifecycle-e2e-verification/41-RESEARCH.md`, `test/integration/quote_integration_test.exs`]

The least-scope, most repo-native execution shape is one opt-in ExUnit module that is excluded from default test runs, uses a real `sk_test_...` key against `https://api.stripe.com`, creates a one-time Price-backed Quote, runs `create -> finalize -> accept`, selects the first available downstream ref in the locked order, retrieves exactly one downstream resource, and stops at typed top-level decode. This matches the repo’s existing excluded integration-tag pattern, reuses `test/support/test_helpers.ex` and `test/support/fixtures/quote.ex`, and avoids a notebook-first workflow on a machine where LiveBook is not installed. [CITED: https://docs.stripe.com/test-mode] [CITED: https://docs.stripe.com/api/quotes/create] [VERIFIED: `test/test_helper.exs`, `test/support/test_helpers.ex`, `test/support/fixtures/quote.ex`, `notebooks/stripe_explorer.livemd`, local command `livebook --version`]

If a real sandbox key is unavailable, or if the chosen sandbox still does not expose a downstream ref for the selected Quote shape, the phase should record that outcome explicitly through a failing opt-in proof command and verifier text rather than mutating Phase 41 claims or broadening into payment/subscription semantics. The repo already has a script/probe precedent for this “document the environment truthfully” posture. [VERIFIED: `.planning/phases/41.1-quote-downstream-follow-through-verification/41.1-CONTEXT.md`, `scripts/verify_portal_endpoint.exs`, `scripts/verify_stripe_mock_reject.exs`]

**Primary recommendation:** Add one env-gated `:external_integration` Quote proof against a real Stripe sandbox, bias the proof toward the `invoice` path by using a one-time Price, and treat “no downstream ref exposed” as an explicit recorded failure. [CITED: https://docs.stripe.com/test-mode] [CITED: https://docs.stripe.com/api/quotes/create] [VERIFIED: `.planning/phases/41.1-quote-downstream-follow-through-verification/41.1-CONTEXT.md`]

### Pattern 1: Env-Gated External Proof Test

**What:** A dedicated ExUnit module tagged separately from ordinary `:integration`, guarded by required env vars, and never run by plain `mix test`. [VERIFIED: `test/test_helper.exs`, `test/integration/opentelemetry_integration_test.exs`, `test/integration/circuit_breaker_integration_test.exs`]

**When to use:** Use this when the planner wants repeatable evidence inside the repo and the maintainer can provide a real Stripe `sk_test_...` key. [CITED: https://docs.stripe.com/test-mode] [VERIFIED: local command `STRIPE_API_KEY=unset`, local command `STRIPE_SECRET_KEY=unset`]

**Example:** [Source: repo tag/exclusion patterns + Stripe testing docs]

```elixir
defmodule LatticeStripe.QuoteDownstreamExternalTest do
  use ExUnit.Case, async: false

  import LatticeStripe.TestHelpers
  import LatticeStripe.Test.Fixtures.Quote

  @moduletag :external_integration

  setup_all do
    api_key = System.fetch_env!("STRIPE_API_KEY")

    unless String.starts_with?(api_key, "sk_test_") do
      flunk("Phase 41.1 proof requires a Stripe test/sandbox secret key")
    end

    start_supervised!({Finch, name: LatticeStripe.ExternalFinch})
    :ok
  end

  setup do
    client =
      test_integration_client(
        api_key: System.fetch_env!("STRIPE_API_KEY"),
        base_url: "https://api.stripe.com",
        finch: LatticeStripe.ExternalFinch
      )

    %{client: client}
  end
end
```

### Pattern 2: Bias the Proof Toward the `invoice` Path

**What:** Create a disposable Product and a one-time Price, then create the Quote from that Price so the first downstream target is most likely `invoice`, which matches the phase’s locked preference order. [CITED: https://docs.stripe.com/api/quotes/create] [CITED: https://docs.stripe.com/api/quotes/accept]

**When to use:** Use this as the default path unless the sandbox shows that the Quote shape you need actually produces `subscription` or `subscription_schedule` first. [CITED: https://docs.stripe.com/api/quotes/accept]

**Example:** [Source: Stripe Quote create/accept docs + existing repo Quote helpers]

```elixir
{:ok, customer} = LatticeStripe.Customer.create(client, %{"email" => unique_email})
{:ok, product} = LatticeStripe.Product.create(client, %{"name" => unique_name})

{:ok, price} =
  LatticeStripe.Price.create(client, %{
    "product" => product.id,
    "currency" => "usd",
    "unit_amount" => 2_000
  })

{:ok, quote} =
  LatticeStripe.Quote.create(client, %{
    "customer" => customer.id,
    "line_items" => [%{"price" => price.id, "quantity" => 1}]
  })

{:ok, _open_quote} = LatticeStripe.Quote.finalize(client, quote.id, %{})
{:ok, accepted} = LatticeStripe.Quote.accept(client, quote.id)

ref =
  cond do
    is_binary(accepted.invoice) -> {:invoice, accepted.invoice}
    is_binary(accepted.subscription) -> {:subscription, accepted.subscription}
    is_binary(accepted.subscription_schedule) -> {:subscription_schedule, accepted.subscription_schedule}
    true -> flunk("No downstream ref exposed: invoice/subscription/subscription_schedule all nil")
  end
```

### Anti-Patterns to Avoid

- **Do not reuse `stripe-mock` as the downstream success environment:** Phase 41 already proved the local mock can return all three downstream refs as `nil`. [VERIFIED: `.planning/phases/41-quote-lifecycle-e2e-verification/41-RESEARCH.md`, `test/integration/quote_integration_test.exs`]
- **Do not default to recurring Price data for the first proof:** recurring prices bias the flow toward subscription semantics and make the `invoice`-first preference harder to satisfy. [CITED: https://docs.stripe.com/api/quotes/accept]
- **Do not retrieve more than one downstream resource:** the locked phase scope stops after one retrieve and typed top-level decode. [VERIFIED: `.planning/phases/41.1-quote-downstream-follow-through-verification/41.1-CONTEXT.md`]
- **Do not make notebook-only evidence the primary deliverable:** the repo notebook is useful for exploration, but the local machine lacks LiveBook and notebook output is weaker verifier input than an explicit command. [VERIFIED: `notebooks/stripe_explorer.livemd`, local command `livebook --version`]

## Common Pitfalls

### Pitfall 1: Proving the wrong downstream path first

**What goes wrong:** The proof uses recurring line items and immediately lands in subscription territory, which makes the `invoice`-first preference harder to satisfy. [CITED: https://docs.stripe.com/api/quotes/accept]  
**Why it happens:** The downstream object depends on the Quote’s billing shape, not on the planner’s preference order. [CITED: https://docs.stripe.com/api/quotes/accept]  
**How to avoid:** Start with a one-time Price-backed Quote so the first expected downstream target is `invoice`. [CITED: https://docs.stripe.com/api/quotes/create]  
**Warning signs:** The accepted Quote returns `subscription` or `subscription_schedule` while `invoice` is `nil`. [VERIFIED: `lib/lattice_stripe/quote.ex`]

### Pitfall 2: Accidental default-suite or live-key execution

**What goes wrong:** A real-network proof runs when someone expected plain `mix test`, or it runs with an inappropriate key. [VERIFIED: `test/test_helper.exs`, `guides/testing.md`]  
**Why it happens:** The repo excludes `:integration`, `:fuse_integration`, and `:otel_integration` by default, but Phase 41.1 would be a new proof surface unless it adds an equivalent guard. [VERIFIED: `test/test_helper.exs`]  
**How to avoid:** Use a dedicated excluded tag and reject non-`sk_test_...` keys in setup. [VERIFIED: `guides/testing.md`, `test/integration/opentelemetry_integration_test.exs`]  
**Warning signs:** The test has no env check, or the command is runnable by plain `mix test`. [VERIFIED: `test/test_helper.exs`]

### Pitfall 3: Over-claiming sandbox semantics

**What goes wrong:** The proof starts asserting payment, activation, webhook, or durable lifecycle semantics that exceed the phase boundary. [VERIFIED: `.planning/phases/41.1-quote-downstream-follow-through-verification/41.1-CONTEXT.md`]  
**Why it happens:** Once a real Stripe environment is involved, it is easy to slide from “typed top-level decode” into “full billing workflow.” [VERIFIED: `lib/lattice_stripe/subscription.ex`, `lib/lattice_stripe/quote.ex`]  
**How to avoid:** Stop immediately after one downstream retrieve and assert only the returned top-level struct type and ID. [VERIFIED: `.planning/phases/41.1-quote-downstream-follow-through-verification/41.1-CONTEXT.md`]  
**Warning signs:** The plan adds webhook listeners, payment assertions, status timing checks, or multiple downstream retrieves. [VERIFIED: `.planning/phases/41.1-quote-downstream-follow-through-verification/41.1-CONTEXT.md`]
