## Summary

Phase 41.1 should be planned as a narrow two-plan follow-up that uses a real Stripe sandbox, not local `stripe-mock`, to prove one downstream reference exists after `Quote.accept/3`. Stripe’s current API reference still states that accepting a quote returns an accepted quote and creates an invoice, subscription, or subscription schedule, while Stripe’s current testing guidance recommends sandboxes as the primary test environment for realistic integration checks. Local Phase 41 evidence already proved `stripe-mock` is the wrong tool for this requirement, so the least-scope credible move is an opt-in sandbox probe that runs through the shipped SDK and stays excluded from default automated test loops. Sources: Stripe Quote accept API and Stripe testing docs opened on 2026-05-25.

**Primary recommendation:** add a repo-local, opt-in `mix run` verification script that uses `LatticeStripe.Client` with `STRIPE_SECRET_KEY` from a dedicated Stripe sandbox, creates a disposable customer/product/quote, finalizes and accepts the quote, then retrieves exactly one downstream resource in the D-41.1-04 preference order. Pair that script with a Phase 41.1 verifier artifact that records the exact environment, command, observed downstream reference type, and typed top-level retrieve result.

## Why This Environment

### Option A: Keep using local `stripe-mock`

Reject.

- Phase 41 already reproduced `invoice=nil`, `subscription=nil`, and `subscription_schedule=nil` after `Quote.accept/3`.
- This would knowingly retry a disproven environment and adds no new evidence.

### Option B: Dashboard-only manual proof

Reject.

- It can show that Stripe created downstream objects, but it does not prove the shipped SDK request/response path.
- This phase is about follow-through proof through LatticeStripe, not only about Stripe account state.

### Option C: Env-gated ExUnit test against real Stripe sandbox

Viable but second-best.

- It gives structured assertions, but it introduces a new class of external-state tests into the repo test tree.
- That raises maintenance surface around secret handling, flakiness, and accidental inclusion in default runs.

### Option D: Env-gated `mix run` probe script against real Stripe sandbox

Recommended.

- Reuses the repo’s existing probe-script pattern in `scripts/verify_portal_endpoint.exs` and `scripts/verify_stripe_mock_reject.exs`.
- Exercises the real SDK path instead of ad-hoc HTTP.
- Avoids polluting the default `mix test` loop with secret-dependent external state.
- Keeps the artifact narrowly operational: one command, one proof, one verifier.

- Do not require repo-wide `mix test` or CI for this phase

## Risks And Mitigations

### Risk 1: Test-mode or sandbox settings differ from local assumptions

Mitigation:

- Prefer a dedicated additional Stripe sandbox, not the shared test-mode sandbox
- Record the environment explicitly in the verifier
- Keep the proof limited to downstream-reference exposure plus one retrieve

### Risk 2: Real Stripe state creates more variability than `stripe-mock`

Mitigation:

- Use disposable resources created inside the script
- Avoid asserting deeper downstream semantics
- Retrieve only one linked resource and stop

### Risk 3: Secret handling or accidental CI coupling

Mitigation:

- Read `STRIPE_SECRET_KEY` from environment only
- Do not commit keys, IDs, or account-specific settings
- Keep the probe as `mix run`, not in default test execution

### Risk 4: The chosen sandbox still does not expose a downstream reference

Mitigation:

- Treat that as a real reproduced outcome
- Fail the script clearly
- Record the outcome in `41.1-VERIFICATION.md` without rewriting Phase 41 history
