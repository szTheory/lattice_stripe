<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Developer -> update_evidence/4 | User-supplied evidence map must not leak `submit: true` to Stripe |
| Stripe API -> from_map/1 | Untrusted string values for status/reason must not create atoms dynamically |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-33-03 | Tampering | `update_evidence/4` | mitigate | `Map.drop(evidence, ["submit", :submit])` strips both string and atom submit keys before delegating to `do_update/4`. Test verifies stripping works. |
| T-33-04 | Denial of Service | `atomize_status/1`, `atomize_reason/1` | mitigate | Uses `defp` clause matching on known string literals. Catch-all `defp atomize_status(other), do: other` passes unknown strings through without calling `String.to_atom/1`. No atom table exhaustion possible. |
| T-33-05 | Tampering | `close/3` | accept | Irreversible action. Mitigated by documentation (`## Irreversibility` section) rather than runtime guards, consistent with `Account.reject/4` precedent. No `:i_understand` atoms per D-10. |
| T-33-06 | Tampering | `submit_evidence/3` | accept | Irreversible action. Mitigated by documentation (`## Irreversibility` section) and separate function name (not a flag on `update/4`). The two-step workflow (stage then submit) is the safety mechanism. |
| T-33-07 | Information Disclosure | `Inspect` protocol | mitigate | Custom `Inspect` hides evidence (may contain PII like customer email, address), metadata, charge, and payment_intent. Shows only id, object, amount, currency, status, reason. |
</threat_model>
