<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Developer params -> Stripe CreditNote endpoints | Raw caller-supplied billing params cross from application code into Stripe requests |
| Operator action -> `void/3` | An irreversible mutation is exposed as a single SDK call |
| stripe-mock behavior -> integration confidence | Test infrastructure may not enforce the same lifecycle rules as real Stripe |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34-04 | T | `create/3`, `preview/3`, `update/4` raw param passthrough | accept | Keep the SDK Stripe-shaped per D-05 and D-06; Stripe remains the validation authority and unit tests only verify request routing, not local policy gates. |
| T-34-05 | R | `void/3` | mitigate | Expose `void/3` as a dedicated verb with no params, require a dedicated `## Irreversibility` doc section, and add request-shape plus lifecycle-aware tests so callers cannot mistake it for a benign update. |
| T-34-06 | D | `list_line_items` and preview-line pagination | mitigate | Reuse `List.stream!/2` and typed `LineItem.from_map/1` mapping; unit tests cover both issued and preview line-item endpoints plus bang helpers. |
| T-34-07 | S | integration tests over-crediting lifecycle semantics because stripe-mock is permissive | mitigate | Helper names and test comments must encode finalized-invoice and open-invoice caveats explicitly, and void assertions allow either Stripe-like error or stripe-mock success while documenting the real constraint. |
</threat_model>
