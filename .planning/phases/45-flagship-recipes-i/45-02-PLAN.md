<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| meter-event request success -> billing truth | A successful API response can be mistaken for authoritative billed state even though downstream validation and reconciliation are asynchronous |
| identifier/idempotency posture -> duplicate usage | Weak event identity or replay handling can lead docs readers into double-reporting or unverifiable correction flows |
| flagship recipe -> canonical metering truth | A runtime-first walkthrough can accidentally over-simplify the deeper metering, webhook, and operator rails if it stops routing readers outward |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-45-04 | T | meter-event success semantics | mitigate | State clearly that accepted requests are accepted for processing, not proof that downstream billing truth is already settled |
| T-45-05 | T | event identity and replay posture | mitigate | Teach stable identifiers, transport idempotency, and correlation metadata as first-class runtime behavior |
| T-45-06 | T | correction and follow-through story | mitigate | Route async failures through webhooks and `MeterEventAdjustment` rather than implying immediate read-after-write confirmation |
</threat_model>
