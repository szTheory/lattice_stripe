<objective>
Ship `LatticeStripe.Webhook.parse_event_notification/4` and its bang variant `parse_event_notification!/4`. These are the public THIN-01 entry points: verify a thin-event (`/v2/events`) payload's HMAC signature against a pre-shared secret + tolerance window, then decode the JSON body into a typed `%EventNotification{}` struct.

Purpose: This is the verification primitive adopters call from their Phoenix controllers (Phase 48 will document the canonical handler). It is **separate** from `construct_event/4` (the snapshot/v1 entry point) because thin-event payloads have a different on-the-wire shape (`object: "v2.core.event"`, ISO 8601 `created`, nested `related_object`). The verify boundary is identical — same HMAC scheme, same secret type, same tolerance machinery — but the post-verify decode targets a different module.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Adversary-controlled HTTP body → `parse_event_notification/4` | Attacker can submit arbitrary bytes + arbitrary Stripe-Signature header. Verify step (`verify_signature/4`) gates all downstream decode. |
| Adversary-controlled timestamp inside signature header | Attacker can replay a previously valid payload + header pair. `check_tolerance/2` (300s default) gates this; `tolerance: 0` opt is testing-only (reconciled in plan 03). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-47-04 | Spoofing | Forged thin-event payload with invalid signature | mitigate | `verify_signature/4` (unchanged, HMAC-SHA256 with `Plug.Crypto.secure_compare/2`) gates decode — no business logic runs on `{:error, _}` (D-07 reuses exact same codepath as `construct_event/4`). |
| T-47-05 | Tampering (replay) | Captured valid payload resent later | mitigate | `check_tolerance/2` enforces 300s default window; `parse_event_notification/4` honors the `:tolerance` opt the same way `construct_event/4` does. |
| T-47-06 | Information disclosure | Telemetry span metadata leaking payload/secret/sig_header | accept | `webhook_verify_span/2` is unchanged from snapshot path; current implementation only logs `:path` per RESEARCH Security Domain V8 — no change in this plan. |
| T-47-07 | Tampering | `parse_event_notification/4` called with a snapshot payload (object: "event") silently decodes a `%EventNotification{}` with mostly-nil fields | accept | Per RESEARCH "Known Threat Patterns" final row + Pitfall 1, defensive `object == "v2.core.event"` discriminator is recommended as a follow-up, NOT v1.5 scope. Documented in moduledoc "Snapshot events vs thin events" section. |
| T-47-SC | Tampering | npm/pip/cargo installs | accept | No package installs in this plan. Phase 47 uses only already-pinned mix.lock deps. |
</threat_model>
