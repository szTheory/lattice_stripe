  <decision>
    Q1 — What shape does the metering fixture promotion take, and which of the six nested fixtures
    become public?
  </decision>

  <context>
    This is a one-way door. Once Hex 1.8.0 tags, these module names are semver-covered public API
    and renaming them is a breaking change.

    Two in-tree authorities conflict:

    - **The in-source header** on `test/support/fixtures/metering.ex:1-6`, written by Phase 64,
      says: move the file to `lib/lattice_stripe/testing/fixtures/metering.ex` and rename the outer
      module to `LatticeStripe.Testing.Fixtures.Metering`. That yields depth-4 names like
      `LatticeStripe.Testing.Fixtures.Metering.MeterEventSummary`.
    - **The established public convention** is flat, ten times out of ten:
      `Testing.Fixtures.TaxCalculation`, never `Testing.Fixtures.Tax.Calculation`. The Tax family
      was deliberately *flattened* when it was promoted.

    65-PATTERNS.md § No Analog Found records that there is no in-tree example of a nested
    `Test.Fixtures.*` module being flattened on promotion, so there is no precedent to copy — which
    is exactly why this is a checkpoint and not a silent planner choice.

    Scope is the second half of the question. The source file holds six modules: `Meter`,
    `MeterEvent`, `MeterEventAdjustment`, `MeterEventStreamSession`, `MeterEventSummary`,
    `MeterErrorReport`. OBJ-02 says "meter objects (incl. the no-`id` summary)" and names no
    specific set. Every module promoted is semver surface the project must keep forever.

    Cost note: if the flat option is chosen, the nine caller files are **not** one-token edits —
    call sites like `Metering.MeterEvent.basic()` change shape too.
  </context>

  <options>
    <option id="flat-three">
      <name>Flat, promote three (RECOMMENDED — 65-RESEARCH.md § Q1)</name>
      <pros>
        Matches the public convention ten-for-ten. Promotes exactly what OBJ-01/OBJ-02 need:
        `Testing.Fixtures.MeterEvent`, `Testing.Fixtures.MeterEventSummary`,
        `Testing.Fixtures.MeterErrorReport`. Leaves `Meter`, `MeterEventAdjustment`, and
        `MeterEventStreamSession` private, so the semver surface grows only where a requirement
        asks. Shortest public names for adopters.
      </pros>
      <cons>
        Contradicts the Phase-64 in-source header (which must then be deleted with a note, not
        silently). Nine caller files need call-site edits, not just alias edits. The source file
        is split into three new files plus a reduced remainder.
      </cons>
    </option>
    <option id="nested-all-six">
      <name>Nested, promote all six — follow the in-source header literally</name>
      <pros>
        Honors the instruction Phase 64 left behind. Simplest mechanical change: one `git mv`, one
        outer-module rename, and nine one-token alias edits. Call sites are unchanged.
      </pros>
      <cons>
        Introduces the project's first depth-4 public fixture names, permanently breaking a
        ten-for-ten convention. Publishes three fixtures (`Meter`, `MeterEventAdjustment`,
        `MeterEventStreamSession`) that no requirement asks for, expanding semver surface for free.
        Requires authoring six real `@moduledoc`s instead of three.
      </cons>
    </option>
    <option id="flat-all-six">
      <name>Flat, promote all six</name>
      <pros>
        Matches the public convention and leaves no private metering remainder, so there is no
        split-brain about where a meter fixture lives.
      </pros>
      <cons>
        Same free semver expansion as nested-all-six — three published fixtures nothing requires.
        Most work: six new files, six moduledocs, all nine callers rewritten.
      </cons>
    </option>
  </options>
